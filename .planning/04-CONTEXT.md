## 1. Executive Summary & Phase Goal

Phase 4 transforms the candidate pairs generated by Phase 3 into high-precision business entity resolutions.

- **Primary Objective**: Score candidate pairs using an optimized LightGBM classifier and apply the **Brutally Strict Confidence & Singleton Gate (BSCSG)** to maximize the competition metric: **Macro $F_{0.5}$**.
- **Key Metric Dynamics**:
  - Precision is weighted $2\times$ heavier than recall.
  - Singletons (entities with zero true matches) represent a significant fraction of records; predicting empty correctly awards **1.0**, while any false match penalizes the entity to **0.0**.
  - Conservative "Walk-Away" thresholding is mathematically optimal.
- **Output Artifact**: `output/matching_results.tsv` formatted strictly as:
  ```tsv
  source1_entity_id\tmatched_entity_ids
  S1-00001\tS2-00047,S3-00812
  S1-00002\tS3-00004
  S1-00003\t
  ```

## 2. Locked Implementation Decisions

Following structured architectural discovery with the user, the following design choices are finalized and locked for downstream planner and execution agents:

### Decision 1: Feature Engineering — RapidFuzz C-Accelerated String & Address Features
- **Module**: [src/features.py](file:///c:/Users/AYUSH/Documents/MLChallenge/src/features.py)
- **Features Extracted per Candidate Pair $(S1_i, Cand_j)$**:
  1. **Name Similarity Features**:
     - `jaro_winkler_sim`: RapidFuzz Jaro-Winkler similarity on clean core names.
     - `token_sort_ratio`: Normalized token sort ratio (resilient to word-order transpositions like "Textiles & Garments" vs "Garments & Textiles").
     - `token_set_ratio`: Token set ratio (resilient to missing or added tokens).
     - `levenshtein_ratio`: Character-level Levenshtein similarity.
     - `exact_name_match`: Binary flag (1 if clean core names are identical, 0 otherwise).
     - `name_len_diff`: Absolute difference in character lengths.
     - `name_token_jaccard`: Jaccard intersection over union of significant name tokens.
  2. **Address & Geographic Features**:
     - `postal_code_match`: Tri-state indicator:
       - `+1.0`: Both entities have postal codes and they match exactly.
       - `0.0`: Either or both entities have missing/empty postal code.
       - `-1.0`: Both entities have postal codes and they conflict (strong negative signal).
     - `address_number_jaccard`: Jaccard overlap between extracted numeric tokens (door numbers, building numbers, suite numbers).
     - `address_token_overlap`: Token intersection ratio of cleaned address words.
     - `address_levenshtein_ratio`: Levenshtein ratio on normalized address strings.
  3. **Metadata & Source Indicators**:
     - `is_source2`: Binary indicator (1 if candidate is from Source 2, 0 otherwise).
     - `is_source3`: Binary indicator (1 if candidate is from Source 3, 0 otherwise).
     - `blocking_rank`: Rank position (1 to 30) of candidate from Phase 3 candidate generation.

### Decision 2: Training Data Construction — Stratified Hard Negative Sampling (1:4 Ratio)
- **Module**: [src/model.py](file:///c:/Users/AYUSH/Documents/MLChallenge/src/model.py)
- **Sampling Strategy**:
  - Extract all positive pairs $(S1_i, Cand_j)$ present in ground truth (`train_ground_truth.tsv`).
  - For each $S1$ entity, sample up to 4 hardest negative candidate pairs retrieved by Phase 3 blocking that are NOT in ground truth (ranked by blocking similarity).
  - Yields a balanced, high-signal training dataset of ~100k–200k pairs, exposing the model to the most confusing false positives without drowning in trivial negatives.
- **Model Architecture**:
  - `LightGBM Classifier` (`LGBMClassifier`):
    - `objective='binary'`, `metric='auc'`, `boosting_type='gbdt'`.
    - Maximum depth 6, number of leaves 31, min child samples 20, learning rate 0.05.
    - 5-Fold Stratified Group K-Fold Cross-Validation (grouped by `source1_entity_id` so an entity never appears in both train and validation folds).

### Decision 3: Brutally Strict Confidence & Singleton Gate (BSCSG) Calibration
- **Calibration Engine**:
  - Search grid for threshold $\tau^* \in [0.70, 0.95]$ evaluated directly against the official `evaluate_predictions` metric ([utils/metrics.py](file:///c:/Users/AYUSH/Documents/MLChallenge/utils/metrics.py)).
  - Select $\tau^*$ that maximizes the out-of-fold **Macro $F_{0.5}$** score.
- **Hard Discrepancy Veto Rules**:
  - **Postal Code Veto**: If both $S1$ and candidate have valid 5/6 digit postal codes and they are different, veto the match to negative (probability $= 0.0$).
  - **Conflicting Door Number Veto**: If both entities have extracted door/building numbers and share zero numbers (e.g. `1795` vs `2100`), apply high-penalty veto.
- **Strict Walk-Away Policy**:
  - For each $S1$ entity, if all candidates have $P(\text{match}) < \tau^*$, predict an empty string `""` (defaulting to singleton).
  - Only candidates exceeding $\tau^*$ and passing the discrepancy vetoes are included in `matched_entity_ids`.

## 4. Verification Plan & Quality Gates

Downstream execution of Phase 4 must pass the following verification gates before marking Phase 4 complete:

1. **Unit Tests (`tests/test_features.py`)**:
   - Verify Jaro-Winkler and Levenshtein metrics on known typo pairs (`Williams` vs `Wilblims`).
   - Verify postal code tri-state matching (`+1.0`, `0.0`, `-1.0`).
   - Verify address number Jaccard overlap on door numbers.
2. **Unit Tests (`tests/test_model.py`)**:
   - Verify LightGBM training and predict loop.
   - Verify BSCSG threshold calibration produces $\tau^* \ge 0.75$.
   - Verify hard veto logic triggers on conflicting postal codes.
   - Verify singletons correctly output empty string.
3. **Validation Harness Pass**:
   - Run `python utils/validate_submission.py --matching output/matching_results.tsv --candidate output/candidate_pairs.tsv --test-dir dataset/test`.
   - Must achieve exit code 0 (`PASS`) with 0 warnings or errors.
4. **Validation Macro $F_{0.5}$ Benchmark**:
   - Measure cross-validated Macro $F_{0.5}$ on training ground truth validation folds.
   - Quality bar target: Macro $F_{0.5} \ge 0.85$.
